# EPOS Webhook Integration — Technical Requirements
## For EPOS Vendor Integration Partner

**Prepared by:** Watan Central Kitchen  
**Date:** May 2026  
**Version:** 1.0

---

## 1. Overview

Watan Central Kitchen requires a webhook-based integration with your EPOS system to receive real-time sales data. When a sale is completed at any of our restaurants, your system should send a POST request to our webhook endpoint with the order details.

**Purpose:** Automatic inventory deduction based on restaurant sales. When items are sold through the EPOS, our system will:
- Receive the sales data
- Map EPOS menu items to our internal inventory recipes
- Deduct ingredient quantities from the restaurant's stock

**Data flow:** One-way — your EPOS system sends data to us. We do not send data back.

---

## 2. Webhook Endpoint

| Detail | Value |
|---|---|
| **URL** | `https://us-central1-watan-e8290.cloudfunctions.net/eposWebhook` |
| **Method** | `POST` |
| **Content-Type** | `application/json` |
| **Authentication** | API Key (see Section 3) |

---

## 3. Authentication

Each restaurant has a unique API key. Include the key in your request using **one** of these methods:

| Method | Example |
|---|---|
| **Header (preferred)** | `x-api-key: wtn_epos_AbCdEfGh_IjKlMnOp_QrStUvWx_YzAbCdEf` |
| **Bearer token** | `Authorization: Bearer wtn_epos_AbCdEfGh_...` |
| **Query parameter** | `?api_key=wtn_epos_AbCdEfGh_...` |

> **Note:** API keys will be generated by our admin team and shared with you per restaurant. If a key is compromised, we will revoke it and issue a new one.

## 4. Request Payload Schema

```json
{
  "order_id": "EPOS-2026-12345",
  "order_date": "2026-05-02T14:30:00Z",
  "event_type": "order_completed",
  "order_total": 45.80,
  "line_items": [
    {
      "epos_item_id": "ITEM-001",
      "epos_item_name": "Chicken Biryani",
      "portion": "Regular",
      "quantity": 2
    },
    {
      "epos_item_id": "ITEM-002",
      "epos_item_name": "Lamb Seekh Kebab",
      "portion": "Large",
      "quantity": 1
    }
  ]
}
```

### Field Definitions

| Field | Type | Required | Description |
|---|---|---|---|
| `order_id` | string | ✅ Yes | Unique identifier for the order. Used for idempotency — sending the same order_id twice will be ignored. |
| `order_date` | string (ISO 8601) | Recommended | Date/time the order was placed. Defaults to current time if omitted. |
| `event_type` | string | No | Type of event. Default: `order_completed`. |
| `order_total` | number | No | Total order value in GBP. Used for reporting only. |
| `line_items` | array | ✅ Yes | List of items sold. Must contain at least 1 item. |

### Line Item Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `epos_item_id` | string | ✅ Yes | Your unique identifier for this menu item. Must be consistent across all requests. This is the key used for mapping. |
| `epos_item_name` | string | ✅ Yes | Human-readable name of the item (e.g., "Chicken Biryani"). |
| `portion` | string | Recommended | Portion/size name (e.g., "Regular", "Large", "Family"). Helps us map to the correct recipe variant. |
| `quantity` | number | ✅ Yes | Number of this item sold. Must be > 0. |

### Alternative Field Names Accepted

We accept multiple field name formats for flexibility:

| Our Standard | Also Accepted |
|---|---|
| `order_id` | `orderId`, `epos_order_id` |
| `line_items` | `lineItems`, `items` |
| `epos_item_id` | `item_id`, `id` |
| `epos_item_name` | `item_name`, `name` |
| `quantity` | `qty` |
| `portion` | `size` |
| `order_date` | `orderDate` |
| `order_total` | `orderTotal` |

## 5. Response Codes

| Status | Meaning |
|---|---|
| `200 OK` | Event received and processed (or duplicate detected) |
| `400 Bad Request` | Missing required fields (`order_id` or `line_items`) |
| `401 Unauthorized` | Invalid, missing, or revoked API key |
| `405 Method Not Allowed` | Request method is not POST |
| `500 Internal Error` | Server error on our side (retry later) |

### Successful Response Example

```json
{
  "success": true,
  "epos_order_id": "EPOS-2026-12345",
  "restaurant": "Watan Tooting",
  "processing_status": "processed",
  "items_processed": 2,
  "items_unmapped": 0,
  "items_failed": 0
}
```

### Duplicate Response

If the same `order_id` is sent again:

```json
{
  "success": true,
  "message": "Duplicate event — already processed.",
  "epos_order_id": "EPOS-2026-12345",
  "processing_status": "processed"
}
```

---

## 6. When to Send Events

- Send a webhook for **every completed order** (not cancelled or voided orders)
- Send **immediately** after the order is completed/paid
- **One request per order** — include all items in a single request

---

## 7. Item ID Requirements

The `epos_item_id` is critical for mapping. Please ensure:

1. **Consistent IDs** — The same menu item must always have the same `epos_item_id` across all requests
2. **Unique IDs** — Each distinct menu item should have a different ID
3. **Stable IDs** — If you update a menu item's name or price, keep the same `epos_item_id`
4. **New items** — When a new menu item is added to the EPOS, it will arrive as "unmapped" on our side. Our restaurant admin will map it to our internal item. No action needed from your side.

---

## 8. Error Handling & Retries

- If you receive a `5xx` response, please **retry with exponential backoff** (recommended: 1s, 5s, 30s, 5min)
- `200` responses should NOT be retried (even for partially processed events)
- `400` and `401` responses indicate a data/config issue — do NOT retry automatically
